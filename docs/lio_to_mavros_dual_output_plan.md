# 双输出模式交接方案与完成边界

此文件将原终端的交接要求落实到仓库。最终接口、数学约定、测试和 Ubuntu 操作入口见
[双模式实施与测试文档](lio_to_mavros_dual_output.md)。

## 已落实的软件范围

1. 保留现有 lio_to_mavros 包和一个 ROS 节点，默认 vision_pose；完整 odometry 为启动时选择的互斥正式模式。
2. 可选完整预览默认关闭，状态独立，不控制旧 pose 的健康与就绪。
3. 按实际 FAST-LIO 外参计算内部 IMU→base_link，补偿 7 cm 安装高度、杆臂速度、姿态/速度和协方差交叉项。
4. 明确输出 B 原点；飞控 IMU 在 B 前方 4 cm 只写入几何核对说明，不重复加进桥接结果，不自动修改 PX4 参数。
5. 保持完整测量时间戳，逐新帧发送，不把 10 Hz 重发成虚假的 30 Hz。
6. 固定参考、仅 yaw 对齐，保留重力；不持续用 PX4 融合输出修正外部观测，不广播预览 TF。
7. 检查输入和外参、协方差、时间、原点跳变、重启序号、正式模式 MAVROS 状态和 TF；故障锁止，禁止解锁初始化。
8. 原位姿逻辑移到专用小类；数学与状态无 ROS 依赖，可独立测试，无新线程/插件框架。
9. catkin 数学与 ROS 回归测试、只读地面检查脚本、onboard 模式参数、就绪脚本和 systemd 操作说明。
10. 提交推送只包含本任务改动，保留用户已有 temp.md。

## 验证顺序与尚待实机完成的工作

顺序固定为：Ubuntu 编译及自动化测试 → 默认旧模式回归 → 预览消息/几何检查 →
本机 MAVROS/TF/PX4 参数核对 → 正式位置姿态地面接入 → 单独决定速度融合 → 后续飞行验证。
本次 Windows 已运行数学及状态 GoogleTest；ROS 编译、rostest 和 Orin/PX4 融合必须在 Ubuntu 完成。

软件测试通过不能代替 LiDAR 原点实测、base_link 与重心关系核对、飞控固件/时钟/创新量验证。
标准 nav_msgs 不携带 reset_counter，当前采用锁止与地面恢复，不承诺无缝坐标重置。
软件不会开启速度融合、解锁、起飞或修改 EGO/px4ctrl/点云输入。
